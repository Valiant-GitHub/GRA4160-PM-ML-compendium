Reading the Data

Cross-method · The preface to every method page. Before you fit anything, you read the data — and what you read decides what you fit. This page runs a concrete exploratory pass over the five datasets the course actually uses (Titanic, Hitters, seeds, WholesaleCustomers, and the sklearn digits) and is organized not by dataset but by diagnostic: data types & dimensionality, missingness, target distribution & class balance, feature scales, multicollinearity, and a linearity check. Each diagnostic shows the real numbers side-by-side and then names the method or workflow step it steers you toward. Every number below is computed live with the course .venv (numpy 2.4.6, pandas 3.0.3, scikit-learn 1.8.0); none is fabricated. Pair this page with the decision dashboard (which method?) and the workflow patterns (which recipe?).

The reading-to-method loop. Reading the data is not a warm-up you do once and forget — it is the first half of every exam answer. Shape tells you whether p rivals n (regularize, reduce). Missingness dictates an imputation or drop step before any model. Class balance decides your metric (accuracy or precision/recall/F1). Feature scales decide whether to standardize (mandatory before distance or variance-based methods). Correlations warn of multicollinearity (Ridge over OLS). (Non-)linearity decides linear vs. tree-based learners. This page makes each of those calls on the course’s own datasets; the workflow patterns page then strings them into runnable recipes.

The local seeds.csv is not the textbook seeds set. The canonical UCI “seeds” dataset is 210 rows × 3 wheat varieties (70 each). The copy in this repo is 140 rows and only 2 varieties (type is 70× class 1 and 70× class 2 — computed), per the dataset-availability note [DATA] in phase0/disagreements.md. Quote 140×8 / 2-variety here, not the 210×3 you may remember from ISL. Likewise, MNIST (the dataset of notebook 19, 70 000 images × 784 pixels) cannot be loaded in this environment — torch/torchvision are absent — so wherever a large high-dimensional image example is needed, this page uses sklearn’s digits (1797 × 64) as the loadable analogue and never quotes MNIST numbers.

Diagnostic 1 — Data types & dimensionality

The first two questions are how many columns of each kind? and how does p compare to n? They decide your very first lines of code (encoding text, dropping IDs) and flag the high-p regime where plain OLS overfits.

Dataset n rows p usable features Numeric Categorical / text Notable
Titanic 891 ~7 numeric + 3 cat Pclass, Age, SibSp, Parch, Fare, + Survived, PassengerId Sex, Embarked (model-able); Name, Ticket, Cabin (need work) PassengerId is an ID, not a feature — drop it
Hitters 263* 16 numeric + 3 cat 16 batting/career counts League, Division, NewLeague many predictors move together (Diag 5)
seeds 140 7 numeric all 7 geometric measurements type is the label small n, clean
WholesaleCustomers 440 6 spend + 2 cat 6 annual-spend columns Channel, Region (integer codes, really categorical) no row labels at all
digits 1797 64 numeric 64 pixel intensities none p=64 is the high-dim case

* Hitters has 322 rows but 59 have a missing Salary; the modelling frame is 263 (Diag 2).

Three type traps to catch on sight. (i) An ID column (PassengerId, row index) correlates with nothing and must be dropped — feeding it to a model is a classic silent bug. (ii) Integer-coded categoricals lie about their type: WholesaleCustomers’ Channel (1/2) and Region (1/2/3) read as int64 but are nominal — treating Region=3 as “three times Region=1” is wrong; one-hot or leave them out of distance/PCA. (iii) Text that is secretly a feature — Titanic’s Name hides a title (Mr/Mrs/Master) and Cabin’s deck letter is informative; raw, they’re unusable, so the course’s preprocessing exercise drops or engineers them (course_materials/Exercises and solutions(VHL)/01_Data_preprocessing_titanic.ipynb).

Where this steers you. When p is large or rivals n — or when many columns are near-duplicates as in Hitters — plain OLS has too much variance; move to Ridge/Lasso (shrink/select) or PCA (compress). digits’ 64 dimensions are the cue for dimensionality reduction before visualization or a distance-based classifier — exactly workflow Pattern D.

Diagnostic 2 — Missingness

You cannot fit on NaN. Which columns are missing, and how much, decides whether you drop rows, drop the column, or impute — and the answer differs sharply across these datasets (all counts computed):

Dataset Column Missing count Missing % Sensible action
Titanic Cabin 687 77.1 % drop the column (or reduce to “has cabin?”)
Titanic Age 177 19.9 % impute (median / by group) — too valuable to drop
Titanic Embarked 2 0.2 % impute mode or drop 2 rows
Hitters Salary (target) 59 18.3 % drop those rows — can’t impute the target
seeds — 0 0 % nothing to do
WholesaleCustomers — 0 0 % nothing to do
digits — 0 0 % nothing to do

Never impute the target, and never impute before you split. Hitters’ 59 missing Salary values are dropped (322 → 263), because inventing a target value would be inventing the answer — this is exactly the row-drop in the OLS and regularization examples. And any feature imputation (Titanic’s Age median) must be learned on the training fold only and applied to the test fold — put the imputer in a Pipeline so it never sees the held-out data, the same leakage rule that governs scaling.

Where this steers you. Missingness is a workflow decision, not a method choice — it sits before every model. The recipe is workflow Pattern F (missing-data handling): drop columns past a missing threshold, impute the rest inside a pipeline, drop rows only when the target is missing.

Diagnostic 3 — Target distribution & class balance

The target’s shape decides two things at once: for classification, whether accuracy is a trustworthy metric; for regression, whether the target is skewed enough to warrant a transform.

Classification targets — is it balanced? (class counts computed)

Dataset Target Class balance Majority-class accuracy Verdict
Titanic Survived 549 died / 342 survived = 61.6 % / 38.4 % 0.616 mild imbalance — watch the metric
seeds type 70 / 70 = 50 % / 50 % 0.50 perfectly balanced
digits 0–9 174–183 per class (≈ 10 % each) 0.102 balanced across 10 classes

Accuracy lies on imbalanced data. A model that always predicts “died” on Titanic scores 61.6 % accuracy (the majority-class rate, computed) while finding zero survivors — useless. The fix is to report precision / recall / F1 and read the confusion matrix, and to consider class_weight="balanced" or stratified splitting (Lecture 5, slide 5). Titanic’s 62/38 split is only mild, but the WDBC tumour data and the exam’s SimulatedData are where this bites hard — see workflow Pattern E (imbalanced classes). seeds and digits are balanced, so accuracy there is honest.

Regression target — is it skewed? Hitters’ Salary is heavily right-skewed (computed): min $67.5k, median $425k, mean $535.9k (mean > median, the skew fingerprint), max $2 460k; sample skewness +1.58. A log transform almost fully fixes it — skewness of log(Salary) is −0.18 (computed). The histogram makes the long right tail visible:

Where this steers you. A balanced target (seeds, digits) ⇒ accuracy is fine; an imbalanced one (Titanic, and worse) ⇒ precision/recall/F1 and stratified splits (Pattern E). A skewed regression target (Hitters’ Salary) ⇒ consider a log transform and remember that squared-error loss in OLS is pulled by the high-salary tail.

Diagnostic 4 — Feature scales (why standardize)

Distance-based and variance-based methods — kNN, K-Means, PCA, and penalized regressions — are not scale-invariant: a feature with a large numeric range dominates the distance or the variance budget purely because of its units. So you must check, per dataset, whether the feature scales differ.

seeds — same family of measurements, but spread differs by orders of magnitude (per-feature std computed):

seeds feature std range (max − min)
area 2.406 9.95
asymmetry_coefficient 1.272 5.92
perimeter 1.099 4.62
grove_length 0.535 2.03
length 0.407 1.77
width 0.283 1.18
compactness 0.016 0.079

The largest standard deviation (area, 2.41) is ≈ 150× the smallest (compactness, 0.016, computed). Untouched, area would single-handedly drive any Euclidean distance and the first principal component.

WholesaleCustomers — the scale problem is even starker because the spend columns are raw kroner-like counts (computed):

Wholesale feature mean median max std
Fresh 12 000 8 504 112 151 12 647
Grocery 7 951 4 756 92 780 9 503
Milk 5 796 3 627 73 498 7 380
Frozen 3 072 1 526 60 869 4 855
Detergents_Paper 2 882 817 40 827 4 768
Delicassen 1 525 966 47 943 2 820

Means differ by ≈ 8× across columns and the standard deviations by ≈ 4.5× (computed) — and on top of that the spends are wildly right-skewed (Diag 3’s logic: Delicassen skew +11.1, Frozen +5.9, computed). By contrast, digits has every feature on the same 0–16 pixel scale, so standardizing matters far less there — a useful counter-example.

Scale before any distance- or variance-based method — full stop. Fit a StandardScaler (mean 0, std 1) inside the pipeline before K-Means, PCA, kNN, or a penalized regression. Without it, PCA on WholesaleCustomers would return “the Fresh axis” as PC1 — a units artefact, not structure — and K-Means clusters would just sort customers by total Fresh spend. This is the reason the exam’s clustering task (Pattern C/D) begins StandardScaler → PCA → KMeans. Tree-based methods (trees, random forests) are the exception — they split one feature at a time and are scale-invariant, so they need no scaling.

Where this steers you. Differing scales (seeds, WholesaleCustomers) ⇒ StandardScaler is mandatory before PCA / K-Means / kNN / regularization. Uniform scale (digits’ pixels) ⇒ scaling is optional. Tree-based learners ⇒ skip scaling entirely.

Diagnostic 5 — Feature correlations / multicollinearity

When predictors carry the same information, a linear model’s coefficients become unstable (large variance, “wrong” signs) even though predictions may be fine. The cure is to measure it before fitting. Hitters is the course’s poster child: its career-total columns are near-duplicates (Pearson correlations computed):

Pair Correlation
CAtBat ↔︎ CHits 0.995
CHits ↔︎ CRuns 0.985
CAtBat ↔︎ CRuns 0.983
CAtBat ↔︎ CRBI 0.951
CRuns ↔︎ CRBI 0.946
AtBat ↔︎ Hits (single-season) 0.964

A correlation of 0.995 between CAtBat and CHits means they are essentially the same column — a player with more career at-bats has, almost deterministically, more career hits. WholesaleCustomers shows the same thing on its spend columns: Grocery ↔︎ Detergents_Paper correlate 0.925, Milk ↔︎ Grocery 0.728 (computed) — retail co-purchasing. seeds and digits are comparatively benign.

Multicollinearity is why OLS coefficients flip sign. On Hitters, OLS returns a negative coefficient for HmRun once Hits/RBI are in the model (computed on the OLS page) — not because home runs lower salary, but because the redundant predictors fight over a shared signal. This is the textbook cue for Ridge, which shares the coefficient across correlated predictors instead of letting them blow up, and the train–test R^2 gap (0.55 → 0.36) it produces is variance you can shrink away. Lasso, faced with a correlated group, arbitrarily keeps one and zeros the rest — useful for sparsity but unstable; Elastic Net is the compromise. See the regularization decision callout.

Where this steers you. Strong multicollinearity (Hitters’ career totals, Wholesale’s Grocery/Detergents_Paper) ⇒ prefer Ridge over OLS, or compress with PCA (which turns correlated features into uncorrelated components by construction). This is the heart of workflow Pattern B (regression with many predictors).

Diagnostic 6 — A linearity check

A linear model assumes the target moves proportionally with each feature. Two cheap checks tell you whether that holds: does a feature relate to the target monotonically and straight, and does a transform improve the linear fit?

Titanic — survival is non-monotone in age (survival rate by age band, computed):

Age band Survival rate n
0–12 0.580 69
12–18 0.429 70
18–30 0.356 270
30–45 0.426 202
45–60 0.407 81
60+ 0.227 22

Survival is high for children, dips for young adults, recovers in middle age, then falls for the elderly — a U-then-down shape, not a straight line. A purely linear-in-Age term would miss the “children first” effect; this is a cue that a tree (which splits Age at a threshold automatically) or an engineered is_child feature may beat a raw linear term.

Hitters — a transform straightens the relationship (correlations computed). Years correlates with raw Salary at 0.40 but with log(Salary) at 0.54; CHits correlates 0.55 with Salary and 0.62 with log(Salary). The lift from logging the target is the signature of a multiplicative (curved) relationship that a transform makes linear — the same skew finding from Diag 3, now framed as a modelling decision.

Linearity decides linear-vs-flexible. Straight, monotone feature–target relationships (or ones a log/polynomial transform straightens) ⇒ OLS / logistic regression / LDA are appropriate and interpretable. Visible curvature or non-monotonicity that you don’t want to hand-engineer (Titanic survival in age) ⇒ reach for decision trees or random forests, which capture thresholds and interactions automatically. The fastest check is a scatter (regression) or a binned-rate table (classification) like the one above — and remember a penalty cannot fix a wrong functional form, only over-fitting.

Where this steers you. Roughly linear / transformable ⇒ linear family; curved or interaction-heavy ⇒ tree family. This is the top fork of the decision dashboard.

Putting it together

Read across the six diagnostics and each dataset announces its method before you fit a thing:

Dataset Headline reading Method it points to
Titanic mild imbalance (62/38), Cabin 77% / Age 20% missing, non-linear in age impute + logistic/tree/RF; F1 not just accuracy
Hitters 263 rows, career totals corr ≈ 0.99, Salary skew +1.58 Ridge/Lasso over OLS; maybe log target
seeds balanced 70/70, scales differ ≈ 150×, no missing scale → K-Means/PCA (ground truth to check against)
WholesaleCustomers scales ≈ 8× / skew to +11, Grocery↔︎Detergents 0.93, no labels scale → PCA → K-Means
digits 64-dim, balanced 10-class, uniform 0–16 scale PCA for dim-reduction, then kNN

This page is step zero of every workflow. Once you have read the data, hand off to the two cross-method pages: the decision dashboard maps your reading (target type, n vs p, balance, scale) to a shortlist of methods, and the workflow patterns page gives the runnable recipe — load → inspect → handle missing → encode/scale → split → baseline → tune by CV → evaluate with the right metric. The diagnostics here are exactly the inputs both of those need. Read first, then choose, then build.

Reading the data is graded. Every Spring-2025 assignment opens with an inspection step that earns marks on its own (phase0/exam_spring2025_notebook.md): Assignment 1 must notice the missing salaries and the correlated career totals before regularizing Hitters; Assignment 2 must standardize WholesaleCustomers before PCA/K-Means because of the scale gap shown in Diag 4; Assignments 3–4 must check class balance and choose precision/recall/F1 over accuracy. Stating what you see and why it dictates the next step is the cheap, reliable way to bank points — do the EDA out loud.
